Where two findings pulled in different directions, this spec takes the safer reading:

- File deletion after a photo is removed runs after the commit, then re-checks under the product lock that no row of the same product uses the same hash before it deletes anything. Deleting inside the transaction would leave a live photo without files if the commit failed.
- A file written for an upload is deleted on failure only if this request wrote it, and the duplicate check runs under the lock before any write.
- Other methods on `/media/` answer a plain 404 (not 405), so the route reveals nothing. Every non-allowlisted `/media/` path, including `/media/` itself, gets the same plain-text, `no-store` 404 `Not found`.
- `media:seed` validates all of `samples.json` before any write and refuses non-https licence or source URLs; a storage-not-ready run of either command exits 1 and writes nothing.
- The audit `actorId` sits in `after` for every media code, so the reorder, alt and variant-link payloads are objects, not bare lists.
- A variant link to a photo that does not exist or belongs to another product gives the same 422, so existence in another product is not revealed.
- A rolled-back API image is not a safe rollback once photos exist (`prisma db push` refuses to drop them and the API will not start). Rollback means restoring the database backup with the old image, or keeping the new image.
- `media:seed` never brings samples back to a product that ever had a photo removed. It uses the existing audit codes, not new ones.
- Sample alt text describes what is visible and states no specifications. It carries no "Foto contoh" prefix, because the storefront caption already says it and thumbnails are labelled without alt text.
- The optional `SHOP_LIVE` start-up switch from the review is not added. The launch checklist and the caption cover the risk.
- `/media/` file names use the shorter-side target in the file name (480, 960, 1600 or the photo's own shorter side), so the nginx allowlist accepts three or four digits.

## Decision

Product photos replace the drawn placeholders on the storefront. Photos live in the existing MinIO bucket, are resized once at upload into WebP copies at three target sizes, and are served from the shop's own address through nginx with a one-year cache. The demo catalogue gets real credit-free sample photos now, shown with a "Foto contoh" caption; each client's Owner, Admin or Marketing staff can upload their own photos later from a new admin "Produk" screen that covers photos and alt text only. The existing drawing stays as the fallback for any product without a photo.

## Goals and success criteria

- Every product listed as approved in Appendix A shows its photos on product cards, the product page, the cart and the account lists; every product not listed shows its drawing. Picking a variant that has its own photo switches the photo. `npm run media:seed` prints the counts (added, skipped) and exits non-zero, writing nothing, if `samples.json` references a file that does not exist or a recorded hash does not match the committed WebP. Variant switching is verified on photos uploaded during the check (B01), not on sample photos, because no multi-variant product has a sample photo (Appendix A).
- Owner, Admin and Marketing can upload, reorder, set the main photo, link a photo to a variant, edit alt text and remove photos. Operations and CS cannot (403 from the API, no menu item). Every change is in the audit log.
- Photos load as resized WebP from `/media/…` on the shop's own domain, with a Cumulative Layout Shift of 0.00 on a category page and a product page at 390 px (Playwright `layout-shift` entries; every `<img>` has `width` and `height` before it loads) and a one-year immutable cache (checked with `curl -I` on `/media/…`).
- No uploaded photo keeps location, camera or other metadata.
- Performance budgets, measured on dev after deploy and recorded with the other checks: (a) the gzipped `GET /v1/catalog` response grows by at most 15 KB compared with the response before this change; (b) a category page at 390 px loads at most 400 KB of image bytes before any scrolling; (c) the product page main photo is at most 150 KB at 390 px; (d) a 5 MB JPEG upload is processed (three WebP copies written and the row saved) in under 5 s on the dev VPS, and API memory does not grow by more than 300 MB during it. If budget (a) is exceeded, the catalogue may list only the main photo and each variant's linked photo per product, with the full `images` array returned by `GET /v1/products/:slug`; this is allowed only if cart, account and card views still show the right photo.
- Existing checks still pass: axe 0 serious or critical, the sign-in check (12/12), the concurrency check (12/12), the Rp587.250 and W00 metrics unit tests.

## Approaches considered

- **A. Resize once at upload, serve through nginx. Chosen.** WebP copies at fixed sizes are made with `sharp` when staff upload, stored in MinIO and served by nginx from `/media` with a one-year cache. Fast on Indonesian mobile networks, nothing new to run on the VPS, one new dependency.
- B. Store originals and resize on request with an image service (imgproxy) in front of MinIO. Rejected: an extra container to secure, update and size, and its signing keys, for about 15 products.
- C. Store and serve originals as uploaded. Rejected: full-size photos (often 2–5 MB) on every card, and time-limited links would defeat the caching from commit `4e13276`.

## 1. Data and storage

New Prisma model `ProductImage`, applied by the `prisma db push` that already runs when the API container starts:

| Field | Type | Purpose |
|---|---|---|
| `id` | `String @id @default(cuid())` | |
| `productId` | `String`, relation to `Product`, `onDelete: Cascade` | Owning product |
| `position` | `Int` | Gallery order; 0 is the main photo. `@@unique([productId, position])`. Committed values are 0–5. The range is enforced by the service, not by a database CHECK (`db push` cannot create one), so the temporary +100 values used while renumbering are allowed. Only the unique key applies in the database. |
| `alt` | `String` | Bahasa Indonesia alt text, 1–125 characters, required (rules in section 2) |
| `hash` | `String` | SHA-256 (hex) of the largest processed copy. `@@unique([productId, hash])` |
| `width`, `height` | `Int` | Real pixel size of the largest copy, used for the `width` and `height` attributes |
| `sizes` | `Int[]` | Shorter-side targets that exist, for example `[480, 960, 1600]` |
| `source` | `String` | `upload` or `sample` |
| `creator`, `licence`, `licenceUrl`, `sourceUrl` | `String?` | Filled for sample photos, empty for staff uploads. `licence` includes the version (for example "CC0 1.0"). Shown in admin only. |
| `retrievedAt` | `String?` | WIB date the sample file was downloaded |
| `licenceCheck` | `String?` | Who checked the licence, and the path of the dated copy of the licence page or the Commons template seen at that time. Sample photos only. |
| `createdAt` | `String` (WIB ISO, like other tables) | |
| `createdBy` | `String` | The same actor string the audit entry uses (`Nama (Peran)`), or `seed` for sample photos |

For staff uploads the rights confirmation is kept in the audit entry (section 2).

`Variant` gains `imageId String?` with a relation to `ProductImage`, `onDelete: SetNull` and `@@index([imageId])`. Prisma needs both sides of each relation: `Product` gains `images ProductImage[]` and `ProductImage` gains `variants Variant[]`. The service also clears variant links explicitly in the delete transaction; `SetNull` stays as a backstop for any other delete path. The API checks that a variant only links to a photo of its own product, under the product lock (section 2).

Existing data and deploy. No product, variant, order or cart row changes except that `Variant` gains the nullable `imageId`. `ProductImage` starts empty. A product with no rows returns `images: []` and the storefront shows the `ProductArt` drawing. Cart, wishlist and order data never store image data; the storefront reads photos from the live catalogue by product id, so a catalogue response cached before the deploy (15 s fresh plus 45 s stale) simply lacks `images` and shows the drawing until it refreshes. `BootstrapService` and the catalogue seed are not changed: the seed upserts products by fixed ids (B01, A01 …), so the ids in `media/products/{productId}/` are stable across restarts and re-seeds. If a product row is ever deleted, its `ProductImage` rows go with it (`Cascade`) and its files stay in the bucket as unlinked files; removing them is outside this change.

Files in the bucket `tian-media` (name from `MINIO_BUCKET`):

- `media/products/{productId}/{hash16}-{target}.webp`, where `hash16` is the first 16 hex characters of the hash and `target` is the shorter-side target (section 2). A changed photo gets a new name, so a cached link never shows the wrong picture.
- Originals are not kept: only the WebP copies, which carry no metadata.
- Every file is stored with `Content-Type: image/webp`. Caching headers are set by nginx (section 3), not on the object.

Bucket policy and start-up:

- The policy is one Allow statement: principal everyone, action `s3:GetObject` only, resource `arn:aws:s3:::${MINIO_BUCKET}/media/*`. It is written with PutBucketPolicy, which replaces any existing policy and never merges, so a broader policy from an earlier `mc anonymous set` is overwritten. After writing, the API reads it back with GetBucketPolicy and compares it by meaning (action, resource and principal sets, not the raw string, because MinIO may re-format the JSON). Listing and every other prefix (for example the existing `health/` check) stay private. MinIO stays off the public internet (ports 9000 and 9001 do not answer from outside, checked 27 Oct 2026); only nginx on the same host reaches it.
- The MinIO access key used by the API must be allowed `s3:PutBucketPolicy`, `s3:GetBucketPolicy` and `s3:DeleteObject` on the bucket. The deploy notes name these rights.
- Start-up never blocks checkout on MinIO. `ObjectStorage.onModuleInit` catches every error from `ensureBucket` and from the policy step, logs one structured line (`event=storage_init_failed`, error class only, no keys or credentials), sets `ready=false` and lets the API start. `ensureBucket` creates the bucket only when `HeadBucket` answers NotFound; any other error (network, auth, 5xx) counts as "storage unavailable" and never triggers `CreateBucket`. The init retries every 30 s until bucket and policy are both in place, then sets `ready=true` and logs `storage_init_ok` once. A policy that cannot be written or read back correctly is treated the same way: the API never leaves a broader or unchecked policy in place. While `ready=false`, upload and delete answer 503 `STORAGE_UNAVAILABLE`; `media:seed` and `media:remove-samples` run the same bucket and policy init once at start, and if storage is not ready they print "Penyimpanan foto sedang tidak tersedia." with the error class, write nothing and exit with code 1. Also while `ready=false`, `/media/` reads fail as a plain 404. Catalogue, cart, checkout, payments and stock are unaffected. `GET /health` reports `storage: degraded` with HTTP 200 instead of failing.

Storage seam. Media code reaches the bucket only through an `ObjectStorage` interface with `putObject(key, buffer, contentType)`, `deleteObjects(keys)`, `exists(key)`, `putBucketPolicy(json)`, `getBucketPolicy()`, `ensurePublicMediaPolicy()` and the existing `ensureBucket`, `putText` and `getText` (`putText` stays for the health check only). The policy builder and the compare-by-meaning check are pure functions in `server/src/media/policy.ts`; `ensurePublicMediaPolicy()` composes them with `putBucketPolicy` and `getBucketPolicy`. The real class in `server/src/storage.service.ts` wraps the S3 client and takes the `S3Client` as a constructor argument, so tests can inject a stub whose `HeadBucket`, `CreateBucket` and policy calls throw. Tests otherwise inject an in-memory implementation that records and returns the policy and has switches to fail the Nth put, any call, or `deleteObjects` only. Any storage exception during upload, delete, seed or the policy step is converted to 503 `STORAGE_UNAVAILABLE` by a wrapper in the media service, so it never surfaces as 500.

The catalogue responses (`GET /v1/catalog`, `GET /v1/products/:slug`) add to each product:

```json
"images": [{
  "id": "…", "alt": "Kabel USB-C hitam melingkar di atas meja", "width": 2400, "height": 1600,
  "src": "/media/products/B01/1a2b3c4d5e6f7a8b-960.webp",
  "srcset": "/media/products/B01/1a2b3c4d5e6f7a8b-480.webp 480w, …-960.webp 960w, …-1600.webp 1600w",
  "sample": true
}]
```

`sample` is present, and true, only for photos with source "sample". There is no credit data in the public payload. Each `srcset` descriptor `Nw` is the shorter-side target N, which is also the number in the file name, even when the copy's real width is larger (landscape). This is deliberate: the browser then picks the copy by the size of the square frame. Each variant adds `imageId` (or omits it). `art` stays for the fallback drawing. `CatalogService.refresh()` includes images ordered by `position`; the domain `Product` and `Variant` types (server, and the web reference copy `web/src/domain/types.ts`, Agent 01's file) gain the optional `images` and `imageId` fields. Like the `products.media` line in `web/src/domain/rbac.ts`, these edits are part of the approved change; `ProductPhoto` reads the new fields, so the type change lands first.

## 2. Upload, processing and access control

Permission `products.media`, granted to `owner`, `admin` and `marketing`, is added to `server/src/domain/rbac.ts` and its mirror `web/src/domain/rbac.ts` (Agent 01's file; this one line is part of the approved change).

New `MediaModule` in `server/src/media/`. All endpoints use the staff cookie, are `private, no-store` (`cache-policy.ts` default) and are covered by the existing cross-site write check in `main.ts`:

| Method and path | Does |
|---|---|
| `GET /v1/admin/products` | Products of both brands with their photos (including licence fields) and variant links |
| `POST /v1/admin/products/:id/images` | Upload one file (multipart field `file`) with `alt` and `rightsConfirmed` |
| `PATCH /v1/admin/products/:id/images/:imageId` | Change alt text |
| `PUT /v1/admin/products/:id/images/order` | Body `{ ids: [...] }`, the full new order; the first becomes the main photo |
| `PUT /v1/admin/variants/:sku/image` | Body `{ imageId: string \| null }` |
| `DELETE /v1/admin/products/:id/images/:imageId` | Remove a photo |

Dependencies, exact versions pinned like the rest of `server/package.json` (the image has no lockfile, so these pins are the only pin): `sharp` 0.33.5 (subject to the `withXmp` check below) in `dependencies` (prebuilt linux-x64 glibc binary, runs on `node:22-bookworm-slim`); `@types/multer` 1.4.12 in `devDependencies`, with `server/tsconfig.json` `types` becoming `["node", "multer"]` so `Express.Multer.File` compiles. Multer itself arrives through `@nestjs/platform-express`. The implementer confirms both versions install before the plan is final. The implementer also confirms that every sharp API used in tests (`withExif`, `withXmp`, `withIccProfile`, `metadata().xmp`) exists in the pinned version. If `withXmp` is missing in 0.33.5, either bump the pin to the first version that has it (re-checking the linux-x64 glibc prebuilt and Node 22, and updating every statement of the pin in this spec and in `server/package.json`) or build the XMP fixture in the test by inserting an APP1 `http://ns.adobe.com/xap/1.0/` segment into the JPEG bytes. The precondition assertion (input carries exif, xmp and icc) stays.

Checks on upload, in order. Each failure returns the standard `{ error: { code, message, details } }` body:

1. Before any body is read: authentication and the `products.media` permission run in a Nest guard (or path-scoped middleware) that executes before the Multer interceptor, reusing `auth.staff()` and the RBAC matrix. No valid staff session gives 401; no permission gives 403. In both cases the body is never read into memory.
2. Multer in-memory with `limits: { files: 1, fields: 2, parts: 4, fileSize: 10 MB }`. A missing file, a wrong field name (the field is `file`) or more than one file gives 422. Exceeding `fileSize` gives 413 `TOO_LARGE`.
3. The product exists (404). `rightsConfirmed` must be the string `true`; anything else gives 422. This is checked before the file is read or processed.
4. Alt text (shared function with PATCH): strip leading and trailing Unicode whitespace and zero-width characters (including NBSP, U+200B, U+200D, U+FEFF); replace tabs, line breaks and other control characters inside the text with a single space. Length is counted in Unicode code points and must be 1 to 125. HTML is stored as plain text, neither stripped nor rejected, and is only ever shown as text (React escaping; no `dangerouslySetInnerHTML`; no raw HTML in `aria-label`). The admin form prefills "Foto {nama produk}", cut at 125 code points. Unicode normalisation is not applied.
5. Type from the file contents, never from the name or the declared type. Read the first bytes before calling sharp. JPEG (`FFD8FF`), PNG (`89504E47`) and WebP (`RIFF....WEBP`) are accepted. An ISO-BMFF `ftyp` box with brand `heic`, `heix`, `hevc`, `mif1`, `msf1` or `avif` gives the HEIC message (415). `<svg`, `<?xml`, `GIF87a`, `GIF89a` and anything else give the generic unsupported-format message (415); SVG is refused because it can carry scripts. HEIC is detected by the byte check and does not depend on sharp being able to open it. Then confirm with `sharp().metadata().format` being `jpeg`, `png` or `webp`. A decode error on a file that passed the byte check gives 422.
6. Size: width and height are read after applying EXIF orientation (swap them when `metadata().orientation` is 5–8). The shorter side must be at least 480 px. At most 40,000,000 pixels (`limitInputPixels`), which also blocks decompression bombs; the check happens before any pixel decoding or resizing. The largest copy's longer side must stay within WebP's 16,383 px limit (for example a 25000×1600 photo is refused); both refusals use the same 422 "terlalu besar" message.
7. Under the product lock (see "Order of work"): not a duplicate of a photo already on the product, and fewer than 6 photos on the product.

PATCH alt text uses the same rule as step 4. An unknown product, photo or variant sku on any image endpoint gives 404; a photo that belongs to another product gives the same 404 on delete and PATCH, so existence is not revealed.

Error mapping. The global `ApiExceptionFilter` keeps a custom code only when the `HttpException` body carries `code`, and maps unknown errors to 500. The global filter is not changed. Every failure in the Error messages table is raised as an `HttpException` with `{ code, message }`:

- `MediaService` wraps its processing and transaction steps and rethrows: Prisma P2002 with `meta.target` containing `position` becomes 409 "Foto lain sedang diunggah. Coba lagi."; P2002 with a target containing `hash` becomes 409 "Foto ini sudah ada di produk ini."; any other P2002 stays 500 because it is a bug; P2003 on a variant link becomes 409 "Foto baru saja dihapus. Muat ulang halaman."; a sharp decode error becomes 422 "File foto rusak atau tidak bisa dibaca."; sharp's pixel-limit error becomes 422 "Foto terlalu besar untuk diproses (maks. 40 megapiksel)."; S3 and connection errors become 503 `STORAGE_UNAVAILABLE`.
- Nest's `FileInterceptor` turns Multer's `LIMIT_FILE_SIZE` into a plain `PayloadTooLargeException` and other multipart faults into `BadRequestException`, both without `code`. A small exception filter applied with `@UseFilters` on the upload route only rethrows the first as 413 `TOO_LARGE` and the second, and a missing `file`, as 422 `VALIDATION` "Pilih satu file foto."

Processing with `sharp` (version pinned above):

- `rotate()` applies the orientation tag. Targets are measured on the shorter side, because every frame on the storefront and in the admin is square and `object-fit: cover` is limited by the shorter side. For each of 480, 960 and 1600 that is not larger than the photo's shorter side, make a WebP copy at quality 80 whose shorter side equals the target (resize by width when the photo is portrait or square, by height when it is landscape; the longer side keeps the aspect ratio, is never cropped and nothing is enlarged). When the photo's shorter side is under 1600 px, that shorter side becomes the largest target (a shorter side of 1200 gives 480, 960, 1200). The target list is de-duplicated and sorted ascending: the ladder values not larger than the shorter side, plus the shorter side itself when it is under 1600 and not already in the list (480 gives [480]; 960 gives [480, 960]; 1200 gives [480, 960, 1200]; 1600 or more gives [480, 960, 1600]). Example: a 3000×2000 photo gives 720×480, 1440×960 and 2400×1600 copies. File names, the `sizes` column and the srcset descriptors use the target; `width` and `height` store the real pixel size of the largest copy. The 480 px minimum, the target ladder and the stored sizes all use the oriented dimensions.
- No `withMetadata()` or `keepMetadata()`, so all EXIF (including GPS and thumbnail), XMP, IPTC and ICC data is dropped from every copy; colours are converted to sRGB.
- The photo is not cropped. Square frames crop it on screen with `object-fit: cover`, and the 480 px minimum guarantees the smallest copy covers a 480 px frame without enlargement.
- The hash is the SHA-256 of the largest copy. The duplicate check runs under the product lock, before any file is written. The same photo uploaded twice to one product is refused ("Foto ini sudah ada di produk ini").

Resource bounds (image work shares the API process with checkout and payment webhooks). The numbers below are starting values; the plan confirms them from a measured peak.

- sharp opens files with `{ limitInputPixels: 40_000_000, failOn: 'error' }` and `animated` left false, so only the first frame is read. A truncated or corrupt file fails decoding and gives 422.
- Image work runs behind an in-process limiter of 2 concurrent jobs. A request that cannot start within 10 s gets 503 `STORAGE_UNAVAILABLE` with a `Retry-After` header. Multer buffers are released as soon as the job ends. sharp is configured at start-up with `sharp.cache(false)` and `sharp.concurrency(2)`.
- Uploads are limited to 20 per staff member per 10 minutes (429 `RATE_LIMITED`, "Terlalu banyak unggahan. Coba lagi nanti."); a trip is logged.
- `docker-compose.yml` gives the `api` service a memory limit, set from a measured peak and at least 1 GB (two 40 MP decodes are about 320 MB, plus the 10 MB buffers and the Node baseline).
- Test: ten parallel 40 MP uploads keep peak memory below the limit, none hangs, and a checkout request issued during the burst still answers in its normal time.

Locking. Every operation that reads or changes a product's photos runs in one `prisma.$transaction(..., LOCKED_TX)` (from `server/src/commerce/order-lock.ts`) and starts with a new `lockProduct(tx, productId)` helper placed next to `lockOrder`. The helper runs `SELECT id FROM "Product" WHERE id = $1 FOR UPDATE` and answers 404 when no row comes back. This covers upload, alt change, reorder, delete, variant link, and the `media:seed` and `media:remove-samples` commands. Where variants are touched (variant link and delete), the transaction then runs `SELECT sku FROM "Variant" WHERE "productId" = $1 ORDER BY sku FOR UPDATE`, the same sorted-SKU order as `lockStock`. No image code path locks an order row, and image code never takes a variant lock before the product lock, so no cycle with order or payment transactions is possible. The photo count, duplicate hash, first free position and reorder id list are read after the lock, never before. The `PUT /v1/admin/variants/:sku/image` endpoint first resolves the owning product of the sku, locks that product, and only then reads the photo. The two unique keys stay as a backstop; their P2002 maps as above.

Order of work, so a failure never leaves a half-finished photo:

- Upload: do the checks and the image processing in memory, with no lock and no writes. Then open one transaction and lock the product. Under the lock, in this order: (1) a row with the same `(productId, hash)` exists: 409 and write nothing; (2) the product already has 6 photos: 409 `LIMIT_REACHED`; (3) pick the first free position (always 5 or lower); (4) write the WebP files and remember which keys this request wrote; (5) insert the row and the audit entry; (6) commit. Two uploads at once on the same product are serialised by the lock; the second sees the true count. If a write fails, delete the keys this request already wrote (best effort), insert no row, write no audit entry and answer 503. If the transaction fails after a write, delete only the keys this request wrote. Because step (1) found no row with this hash, those keys are not used by any row of the same product. A key is never deleted when a row of the same product references it. A failed cleanup delete is logged and does not change the response.
- Renumbering. One shared service method renumbers a product's photos: first set every photo of the product to `position + 100`, then write the final positions 0 to n-1 in the wanted order. Reorder, delete and sample removal all use it, in the same transaction as their other writes, so the unique key never collides mid-way and no position above 5 is visible after commit. A single decrementing UPDATE is never used.
- Reorder: lock the product, then validate the body. `ids` must be an array of strings, otherwise 422 "Daftar urutan foto tidak valid." The set must equal the product's current photo ids with no duplicates. Anything else (duplicate, missing, extra, another product's id, unknown id, empty list on a product with photos) gives 409 "Urutan foto berubah. Muat ulang halaman." without saying which ids exist. An empty list on a product with no photos is a no-op that returns 200 and writes no audit entry. Then renumber.
- Delete: lock the product, then lock the product's variants in sku order. Delete the row, clear variant links (`variant.updateMany` to null, with `onDelete: SetNull` as backstop), renumber the rest (so the next photo becomes position 0 and the main photo) and write the audit entry. Commit. Then remove the files in a second short transaction that takes the product lock again and deletes the keys only if no row of the same product has the same hash (this closes the race with a quick re-upload of the same photo). Each failed file removal is retried up to 3 times. If a file still cannot be deleted, write an audit entry `PRODUCT_IMAGE_FILE_DELETE_FAILED` (object `productId`, after = the undeleted keys) and log it at error level; the response stays 200, the photo is already gone from the storefront and the catalogue, and only the file remains. Deleting the last photo leaves the empty state.
- Variant link: lock the product, then the variants. Unknown sku: 404. An `imageId` that does not exist or belongs to another product: 422 "Foto tidak milik produk ini." (same text for both). Linking a variant to the photo it already has, or setting null when already null, returns 200 and writes no audit entry. Otherwise update `Variant.imageId` and write `VARIANT_IMAGE_LINKED`.
- After every change, `CatalogService.refreshAfterWrite()` rebuilds the in-memory catalogue snapshot. The storefront then sees the change within about 60 seconds (`max-age=15` plus `stale-while-revalidate=45` in `cache-policy.ts`). A failed rebuild is logged and not retried until the next write or an `api` restart; the admin response still succeeds. A shopper whose cached catalogue still lists a deleted photo gets a 404 for the file and sees the drawing through `onError` until the catalogue refreshes. Browsers that already loaded the file keep it for up to one year (`immutable`), so a licence takedown cannot be forced on returning visitors.

Audit. Codes: `PRODUCT_IMAGE_ADDED`, `PRODUCT_IMAGE_REMOVED`, `PRODUCT_IMAGE_REORDERED`, `PRODUCT_IMAGE_ALT_CHANGED`, `VARIANT_IMAGE_LINKED`, `PRODUCT_IMAGE_FILE_DELETE_FAILED`. The object is the `productId` for every media code except `VARIANT_IMAGE_LINKED`, whose object is the variant SKU. Every media entry is written in the same transaction as the row change (the file-delete-failed entry follows the commit it refers to) and carries `actorId` (the staff id, or `cli` for the commands) inside `after` (`PRODUCT_IMAGE_ADDED`, `PRODUCT_IMAGE_REMOVED`, `PRODUCT_IMAGE_REORDERED`, `PRODUCT_IMAGE_ALT_CHANGED`, `VARIANT_IMAGE_LINKED`, `PRODUCT_IMAGE_FILE_DELETE_FAILED`), so attribution survives a staff rename. `after` is never null for a media code except where the table says null; removal carries `actorId` in `after`. The existing `name (Role)` actor string format stays unchanged.

| Code | before | after |
|---|---|---|
| `PRODUCT_IMAGE_ADDED` | null | `{ imageId, position, alt, hash, sizes, width, height, source, rightsConfirmed (uploads), uploadedBytes, uploadedFilename (as sent, cut to 120 characters, stored only here and never used in a storage key), actorId }` |
| `PRODUCT_IMAGE_REMOVED` | the full removed row | `{ actorId }` |
| `PRODUCT_IMAGE_REORDERED` | `{ ids: [...] }` | `{ ids: [...], actorId }` |
| `PRODUCT_IMAGE_ALT_CHANGED` | `{ imageId, alt }` | `{ imageId, alt, actorId }` |
| `VARIANT_IMAGE_LINKED` | `{ imageId or null }` | `{ imageId or null, actorId }` |
| `PRODUCT_IMAGE_FILE_DELETE_FAILED` | null | `{ keys, actorId }` |

For staff uploads `rightsConfirmed: true` in the `PRODUCT_IMAGE_ADDED` entry shows who confirmed the right to use the photo, and when. The commands write to the same audit store; their actor is `CLI: {operator}` (section 5).

Operational log. Every upload, delete and compensation writes one structured Nest `Logger` line (no new dependency, no new table) with `event`, `productId`, `imageId` when known, `staffId`, `bytes`, `durationMs`, and for failures `errorClass` and `leftBehindKeys`. Events: `media_upload_ok`, `media_upload_rejected` (with the rule that failed), `media_processing_failed`, `storage_unavailable`, `media_delete_files_failed` and `media_compensation_failed`; the last two are logged at error level with the full key list, so the orphan-file cleanup deferred to a later round can be built from the log. The log never holds file contents, client-supplied filenames, alt text or credentials. The audit log stays the only record of who changed what.

## 3. Serving and caching

- `web/nginx.conf` gains an allowlist location `location ~ "^/media/(products/[A-Za-z0-9_-]+/[0-9a-f]{16}-[0-9]{3,4}\.webp)$"`. The whole regex is in double quotes because it contains braces; nginx reads an unquoted `{` as the start of a block and `nginx -t` fails. It allows only GET (`limit_except GET { deny all; }`; HEAD is implied), strips the visitor's `Cookie` and `Authorization` headers (`proxy_set_header Cookie ""; proxy_set_header Authorization "";`), and sets `rewrite ^/media/(.*)$ /${MINIO_BUCKET}/media/$1? break;` followed by `proxy_pass ${MEDIA_UPSTREAM};` with no URI part and no runtime variables, so no `resolver` is needed. The trailing `?` stops nginx forwarding the query string, so S3 response-override parameters never reach MinIO. `proxy_next_upstream off`. Any other `/media/…` path (including `/media/`, `/media/products/`, odd encodings and any key not matching the pattern) is answered by `location /media/ { error_page 404 = @media_404; return 404; }` from nginx without contacting MinIO, so it gets the same plain-text, `no-store`, `nosniff` 404 as every other failure (below) and not nginx's default HTML page.
- Errors: `proxy_intercept_errors on; error_page 400 401 403 404 405 500 502 503 504 = @media_404;` and, at server level, `location @media_404 { internal; default_type text/plain; add_header Cache-Control "no-store" always; add_header X-Content-Type-Options "nosniff" always; return 404 "Not found"; }`. MinIO's 403 and 404, a refused method, a stopped MinIO and any other upstream failure all become this one plain 404 with no MinIO body or headers.
- Success headers: `proxy_hide_header` is listed one header per line, because nginx accepts no wildcard: `Server`, `Cache-Control`, `Set-Cookie`, `x-amz-request-id`, `x-amz-id-2`, `x-amz-version-id`, `x-amz-server-side-encryption`, `x-minio-deployment-id`, `x-minio-error-code`, `Strict-Transport-Security`, `X-Xss-Protection`, `Content-Security-Policy` and `Vary`, plus any other `x-amz-*` or `x-minio-*` header seen in `curl -I` against dev. `ETag` and `Content-Type` are kept. nginx then adds its own single `Cache-Control: public, max-age=31536000, immutable` and `X-Content-Type-Options: nosniff` with `add_header` and without `always`, so they are never sent on error responses.
- Configuration per client fork. The web service in `docker-compose.yml` gets `extra_hosts: ["host.docker.internal:host-gateway"]` (as the API service has) and `environment: ["MINIO_BUCKET=${MINIO_BUCKET:-tian-media}", "MEDIA_UPSTREAM=${MEDIA_UPSTREAM:-http://host.docker.internal:9000}", "NGINX_ENVSUBST_FILTER=^(MINIO_BUCKET|MEDIA_UPSTREAM)$"]`. `env_file: ./server/.env` is never used on web: the web container must not receive MinIO keys, the database URL or signing secrets. Compose reads `${…}` from the root `.env` or the shell, not from `server/.env`, so the root `.env.example` documents both variables; `MINIO_BUCKET` must equal the value in `server/.env`, and a fork whose MinIO is on another host or port sets `MEDIA_UPSTREAM` to match its `MINIO_ENDPOINT`. The compose defaults are required: nginx's start-up `envsubst` only fills variables that are set, and an unset one would break `proxy_pass`. `server/.env.example` gets no new keys. The photo limits (10 MB, 6 photos, 480 px minimum, 40 megapixels, quality 80, targets 480/960/1600) are constants in `server/src/media/limits.ts`, not environment variables (`MAX_UPLOAD_BYTES = 10 * 1024 * 1024`, that is 10 MiB, shown as "10 MB" in copy; nginx `client_max_body_size 11m` is 11 MiB; the boundary test uses this constant), so every fork behaves the same; a changed file-size limit also needs a matching `client_max_body_size` (limit plus 1 MB).
- `web/Dockerfile` changes `COPY nginx.conf /etc/nginx/conf.d/default.conf` to `COPY nginx.conf /etc/nginx/templates/default.conf.template`, and nothing is copied to `conf.d`. The official image's start-up `envsubst` writes the rendered `/etc/nginx/conf.d/default.conf`; the filter above leaves nginx's own `$uri` and similar variables untouched. `web/Dockerfile` is among the changed files.
- Body limit. `location /v1/` keeps nginx's default `client_max_body_size` of 1 MB. A second location, `location ~ ^/v1/admin/products/[^/]+/images$`, sets `client_max_body_size 11m;`, repeats the proxy lines of `/v1/` (`proxy_pass http://api:8080;`, `proxy_http_version 1.1;`, `Host` and `X-Forwarded-Proto`, because a regex location does not inherit them), allows POST only (`limit_except POST { deny all; }`) and sets `error_page 413 = @too_large;`. A named location returns JSON: `{"error":{"code":"TOO_LARGE","message":"Ukuran file maksimal 10 MB.","details":[]}}` with status 413. The 11 MB limit leaves room for multipart overhead on a 10 MB file; Multer returns the same body for files between 10 and 11 MB. The web client also pre-checks size and treats any 413 or non-JSON error body as `TOO_LARGE` or a generic error (section 4).
- The `/v1/admin/...` image endpoints stay `private, no-store`; the catalogue keeps `public, max-age=15, stale-while-revalidate=45`.
- Every `<img>` has `srcset` and `sizes`, `width` and `height` (the largest copy's real pixel size, only to give the browser the intrinsic ratio) and `decoding="async"`. The square frame, not the attributes, prevents layout shift.

| Place | `sizes` | Loading |
|---|---|---|
| Catalog cards (`Catalog.tsx`: 2 columns below 1024 px, 3 from 1024 px, 4 from 1280 px, 220 px sidebar from md) | `(min-width: 1280px) 25vw, (min-width: 1024px) 33vw, 50vw` | lazy |
| Home cards (`Home.tsx`: 4 columns from md) | `(min-width: 768px) 25vw, 50vw` | lazy |

| Product page thumbnails | `48px` | lazy, `fetchpriority="low"` |
| Cart rows (`CartPage.tsx`, 80 px column) | `80px` | lazy |
| Search results cards (`SearchPage.tsx`: 2 columns, 4 from 1024 px) | `(min-width: 1024px) 25vw, 50vw` | lazy |
| Account recommendation rows (`Account.tsx`, `w-14`) | `56px` | lazy |
| Account wishlist rows (`Account.tsx`, `grid-cols-[72px_1fr]`) | `72px` | lazy |

The 480 px copy is the smallest; thumbnails and rows all use it. `ProductPhoto` takes `sizes` as a required prop, and `ProductCard` takes an optional `sizes` prop that defaults to the Home value. If a layout's grid classes change, update its `sizes` here and in the code.

The storefront is client-rendered, so the main photo URL is known only after the catalogue response; no preload or server rendering is added in this round. `fetchpriority="high"` on the main photo is the LCP measure. Product-page thumbnail `<img>` tags are rendered only after the main photo's `onLoad` or `onError` fires, so they never compete with it.

## 5. Demo photos and removal

- Sources: Wikimedia Commons and Openverse first (searched with the project's `.claude/skills/design-taste-frontend/scripts/assets.mjs`), Unsplash and Pexels as a backup.
- Accepted licences, and no others: CC0 1.0, Public Domain (including Commons `PD-self`), Unsplash License, Pexels License. No CC BY, CC BY-SA, NC or ND photo is used (owner decision of 28 Oct 2026). The exact licence and version are recorded per photo.
- Rejected: visible third-party brands or logos; identifiable people or body parts; recognisable private property, buildings, artworks, packaging or product designs of other makers; photos of screens, posters, book covers or other works; watermarks; Wikimedia files carrying `{{Trademarked}}`, `{{Personality rights}}`, `{{Non-free}}` or an `{{FoP-…}}` dependency; and any file whose licence is not accepted above. A CC licence from the uploader does not clear third-party rights in the depicted subject, so the subject is checked as well as the licence. Unsplash and Pexels photos are used only as sample images inside the template and are never offered as a standalone set; their licences do not allow implying endorsement or showing people or trademarks in a bad light.
- The owner approves the exact list (Appendix A) before anything is downloaded. Each approved photo is then looked at before it goes into the seed; a product without a safe photo keeps its drawing. For Unsplash and Pexels photos, a dated copy of the licence page is recorded (`licenceCheck`).
- Sample alt text (the `alt` field in `samples.json`) describes only what is visible: object type, colour and setting. It states no length, capacity, volume, model or material, because the sample may not match the variant being sold. Alt text is approved with the photo. Staff uploads keep the prefill "Foto {nama produk}".
- The approved photos are processed with the same code as staff uploads and committed, already as WebP, to `server/seed/media/`. `server/seed/media/samples.json` holds one entry per photo, with a `files` array of its WebP file names and: product, position, alt text, variant SKUs, creator, licence, licence URL, source URL, `retrievedAt` and `licenceCheck`. Files are named `{hash16}-{target}.webp`. Roughly 5 MB in total.
- The two commands are TypeScript in `server/src/media/cli/seed.ts` and `server/src/media/cli/remove-samples.ts`, compiled by `npm run build` and run as `node dist/media/cli/seed.js` and `node dist/media/cli/remove-samples.js`; `server/package.json` gets `media:seed` and `media:remove-samples` scripts for them. They are not placed in `server/scripts/` (the API image does not copy it) and need no tsx. They read `seed/` from the app root (`/app/seed`, resolved from `process.cwd()`), not from `dist/`. `server/Dockerfile` gets `COPY seed ./seed` immediately after `COPY src ./src` and before the line that runs `npx prisma generate && npm test && npm run build`, so any test that reads `samples.json` passes during the image build.
- `npm run media:seed` (inside the API container on a server) is run by hand and never on deploy or container start. Per photo it reads the committed files, computes the SHA-256 of the largest copy and takes width, height and sizes from the files. Before any write it validates every entry of `samples.json` (file present, `hash16` and target match the file name and content, variant SKU exists on the product, licence URL and source URL start with `https://`). If any entry fails it exits 1 and writes nothing for any product. After validation passes, products are processed one by one; a storage or database failure part-way is repaired by running the command again. It uploads only objects missing from MinIO and adds rows with `source: "sample"` and `createdBy: "seed"` only to products that have no photos and no earlier `PRODUCT_IMAGE_REMOVED` audit entry, so it never brings samples back after `media:remove-samples` or after a client removed a photo. Each row gets a `PRODUCT_IMAGE_ADDED` audit entry in the same transaction. It takes the product lock; if a staff upload got there first, the product is skipped and logged. It never changes or removes a client's uploads, and running it twice changes nothing. It prints counts (added, skipped). With `--repair-files`, `media:seed` re-uploads any missing WebP object of existing `source: "sample"` rows from `server/seed/media/` (checked by hash and file name), changes no row and writes no audit entry.
- `npm run media:remove-samples -- --operator "<nama>"` deletes every `source: "sample"` photo (rows and files) through the same delete service method as staff delete, so audit entries, variant-link clearing and renumbering behave identically (position 0 is always the main photo afterwards; products left with no photos fall back to the drawing). It writes one `PRODUCT_IMAGE_REMOVED` entry per photo. `--operator` is required here because the command is destructive; `media:seed` accepts it as optional and falls back to the OS user name. The actor is `CLI: {operator}`. A run that changes nothing writes no entries.
- Both commands run in their own Node process, so they cannot refresh the API's in-memory catalogue. After either one the operator restarts the API (`docker compose restart api`) and confirms `GET /v1/catalog` shows the expected images. No new endpoint is added.
- Launch checklist. `docs/07-delivery/LAUNCH_CHECKLIST.md` does not exist yet; this change creates it (title "Daftar periksa sebelum peluncuran", English section headings) with a "Before launch" section and a row for it in the `docs/README.md` index under A6 (`07-delivery/`). Its items: (1) "Ganti atau hapus foto contoh": run `npm run media:remove-samples -- --operator "<nama>"` inside the API container, restart the API, confirm `SELECT count(*) FROM "ProductImage" WHERE source = 'sample';` returns 0 and `GET /v1/catalog` has no `sample` photos (the implementer matches table and column names to `schema.prisma`); (2) "Foto sudah dicadangkan": a copy of the bucket's `media/` prefix exists off the MinIO volume and the staff know to keep their original photo files; (3) a note that photos removed from the shop stay in returning visitors' browsers for up to a year.

## Rollout on dev

This change is roll-forward only. `db push` adds the table and column without data loss, but once photos exist an older API image would try to drop them, `db push` refuses without `--accept-data-loss`, and the API does not start. `--accept-data-loss` is never added to the container command. Rolling back `web` alone is safe: the storefront shows the drawing for a product whose `images` is empty or missing, or whose image fails to load. Rolling back `api` means restoring the pre-deploy database backup together with the old image, or keeping the new image and hiding the feature.

1. Back up before every deploy of `api`, starting with the first start of the new image (this is the standing deploy backup step until B9): Postgres as before, the `media/` prefix of the bucket copied to a dated folder off the MinIO volume (for example `mc mirror <alias>/${MINIO_BUCKET}/media ./backup/media-YYYYMMDD`, or a copy of the MinIO data directory; the target path is filled in by the operator), and a dated listing of the bucket (`mc ls --recursive`) so uploads can be compared after a failure.
2. Deploy `api` first (new table, nullable `Variant.imageId`, bucket policy at start-up). Confirm `/health` reports storage ok and that an anonymous GET of a `media/*` object works while `GET /media/` stays 404. Never deploy `web` before `api`.
3. Deploy `web` (new `/media/` locations, narrower body limit, template config). Check the config with the template mounted and the variables set, so the image's entrypoint renders it before `nginx -t` runs: `docker run --rm --network tian_default --add-host host.docker.internal:host-gateway -e MINIO_BUCKET=tian-media -e MEDIA_UPSTREAM=http://host.docker.internal:9000 -e NGINX_ENVSUBST_FILTER='^(MINIO_BUCKET|MEDIA_UPSTREAM)$' -v <path>/web/nginx.conf:/etc/nginx/templates/default.conf.template:ro nginx:1.27-alpine nginx -t`. The older handoff command that mounts the file at `/etc/nginx/conf.d/default.conf` is not used, because it skips substitution and would test a literal `${MINIO_BUCKET}`. After the rebuild, `docker compose exec web nginx -t` passes and `docker compose exec web grep -n "media/" /etc/nginx/conf.d/default.conf` shows the real bucket name with no `${…}` and no `//media/`. The rendered file is checked with `nginx -t`; a regex containing `{ }` must be quoted, and the rendered `default.conf` must still show the quoted `/media/` regex with its braces after `envsubst` (the filter leaves `$` and braces alone). If either check fails, do not send traffic to the new web image.
4. `docker compose exec api npm run media:seed`, then `docker compose restart api` and confirm `GET /v1/catalog` returns images for seeded products. The post-deploy check requests one seeded file through the web origin; if it does not return 200, stop with "Gambar tidak dapat dimuat lewat /media; periksa MEDIA_UPSTREAM dan MINIO_BUCKET." and print the upstream URL used. If `media:seed` fails halfway, run it again; it is safe to repeat.
5. Run the checks above. If one fails, record it in the deploy notes, then roll back `web` first, and `api` only if the failure is on the API side.

## Risks

- A wrongly labelled licence (most likely on Flickr): only credit-free licences are used, the verifier step, the owner's approval of Appendix A, a dated copy of each licence page and the recorded source of every sample photo.
- Sample photos left on a live client shop and read as the client's own product: the "Foto contoh" caption, the admin banner, the launch checklist and the removal command.
- Loss of the MinIO volume. Only the three WebP copies of each photo are kept (no originals). If the bucket is lost, every `ProductImage` row and catalogue `src` points at missing files and the storefront falls back to the drawing; staff uploads cannot be recovered from the database. Sample photos are restored by restoring the `media/` backup, or by `npm run media:seed -- --repair-files` for products that still have their sample rows; staff uploads can only come from the backup. Until the B9 backup work, each deploy's backup step copies the `media/` prefix off the volume (Rollout, step 1), the admin photo screen tells staff to keep their original photo files, and the launch checklist has an item for it.
- A removed photo stays fetchable by anyone who holds its URL until its files are deleted, because the bucket policy allows anonymous reads of `media/*`. Browsers that already stored it keep it for up to a year (the approved one-year immutable cache is unchanged). Delete retries the file removal and, if it still fails, records `PRODUCT_IMAGE_FILE_DELETE_FAILED` for manual removal; the URLs carry an unguessable 16-hex hash and nginx has no shared proxy cache. A photo with a privacy or licence problem must not be uploaded in the first place; the upload area and the rights checkbox say so.
- Staff upload third-party images they do not own: the rights checkbox, the audit entry that records who confirmed it, and the warning text. This is a control, not a legal clearance.
- `sharp` is a native module: its prebuilt Linux binary runs on the `node:22-bookworm-slim` image, and the image build runs the tests that use it. Image work shares the API process with checkout; the job limiter, the upload rate limit and the container memory limit bound it.
- Unlinked files after a failed delete or a deleted product: nothing links to them; a cleanup job is listed below as later work, and the error-level log lists the keys.
- Gzip of personal JSON once TLS is on (from the caching review) does not change here; `/media` images are not compressed by nginx (WebP is already compressed).
